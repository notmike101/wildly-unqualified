## Minimal transaction order

1. **Authenticate and reserve the transition.** Parse exact command keys/world ID/sequence, require the admitted connected host and exhibition, and refuse any `pendingPhotos` or pending-thumbnail album entry. Keep the next-reserve branch before the generic paused/exhibition rejection in `applyCommand` (`game.ts:764`). The server owns asynchronous I/O; the game layer should only validate/create the request/candidate. Set `transitioning` and one transition promise synchronously. Duplicate attempts cannot launch two transactions.
2. **Drain, then freeze the completed evidence.** Prevent the producers listed above from entering. Await already-running HTTP mutations without self-deadlocking, recheck current host/world/exhibition/pending capture state, then `await flush()` to drain and persist all older run snapshots. Capture explicit old run/images/physics references. Copy image bytes and use the same validated restart-safe serialization as `saveRun`; do not hand an async writer live mutable objects. Inputs/grips remain neutral, but completed evidence and favorites are unchanged.
3. **Publish an immutable archive.** Store a complete schema-3 document (blueprint, run, photos) under the private archive directory, using only validated server-generated identifiers. Use a sibling staging file plus a no-overwrite publication operation, not `replace()`—the existing helper intentionally replaces targets and rotates backups. One native option is writing/syncing a staging file and exclusively hard-linking it to its final same-filesystem name; an existing destination must be read, validated and compared before reuse. Any filesystem without the required publication operation reports failure and retains the old outing. Preserve failed staging evidence; never overwrite a mismatched archive or delete it to make retry pass.
4. **Prepare the new outing completely.** Generate with a fresh outing ID even if the seed repeats; validate blueprint/objectives and construct the paused camp run plus native physics before publishing anything current. Preserve host ID, every reserved player ID/name/slot and room/session credentials, including pending admission identities. Copy identity, not old positions/goals/gear/album/cooldowns. Keep sequence handling coherent with client world installation; retaining each player's accepted lastSeq is simplest. An empty new image map and new photo namespace are required. Candidate preparation failure disposes candidate physics only.
5. **Durably publish candidate through the same run queue.** Serialize/validate the candidate and enforce the full 8 MiB bound BEFORE I/O. Write it through the existing single-path serialized replacement so the previous completed primary remains a valid backup. No old flush can be enqueued during this step. The successful primary-file publication is the commit point.
6. **Install immediately after commit.** Swap run/images/physics together with no await, reset world-scoped heard/alert caches, input/capture bookkeeping and simulation timing, reconcile sockets, then deliver matching world/hash before snapshots. Release the transition gate. Dispose old physics after the swap; isolate disposal/socket delivery errors from transaction rollback. Failed recipients reconnect against the committed world. Preserve sessions and existing sockets; no new identity/admission cycle is required.
7. **Failure handling is commit-aware.** Before publication, dispose candidate resources, keep the old bundle/evidence, reconcile deferred disconnects, clear the gate and report a retryable error. Existing matching archives may remain for retry. After confirmed publication, never resume/save the old bundle. If an I/O result is ambiguous after rename, read/validate the primary's world ID before deciding; if it is the candidate, install it, and if undecidable keep mutation paused with an explicit storage error. Do not catch a broadcast/disposal failure and overwrite the newly committed primary with old state.

### Archive retry identity

Do not blindly compare full live JSON at `archives/<worldId>.json`: retries change `lastSeq`, and connection/pause fields can change; legitimate favorite edits after a failed attempt are still permitted by “old outing usable.” Recommended simple filenames contain **world ID plus a digest of canonical archive content**. Exclude transient connection/input/sequence/pause bookkeeping from archive identity; include blueprint/content identity, earned album metadata/favorites, JPEG hashes, completed objectives and persistent world state. Unchanged evidence reuses the same validated immutable archive; changed favorites produce a new immutable snapshot name rather than replacing history. A mismatched existing target is always an error. This avoids permanently blocking a later retry merely because the host used the still-usable old exhibition after storage failed. No archive browser, database or general transaction framework is needed.

**Proposed concrete ruling, confirmed by controller for Task 6 preparation:** this naming fits approved spec lines 147–149. Derive canonical content from the existing save sanitization, removing only transient transport bookkeeping for identity comparison. Never exclude favorites, credits, world/blueprint or image bytes; hash the complete retained JPEG bytes as part of that content. Validate an existing exact target and compare its canonical content before reuse, rather than trusting its filename. A retry after a process crash can reuse the durable matching archive. A materially edited completed exhibition can add another full archive (up to the per-save limit), so disk use grows with such revisions; an out-of-space failure must leave old primary/earlier archives intact and report the error, not reclaim history automatically. This is a proposed implementation ruling, not implemented behavior.

### Crash/backup semantics to preserve explicitly

`save.ts:810` validates the prior primary, writes `.tmp`, copies a valid prior primary to `.bak.tmp`, renames the backup, then renames the new primary. `loadRun:773` prefers a valid primary, uses `.bak` for non-version corruption/missing data, and refuses unsupported versions without rewriting. Startup also refuses silently recreating a missing established outing and checks room/run host identity (`server.ts:169`). Therefore a process interruption before primary publication loads the old run; one after publication loads the new run, with completed archive/backup retained.

The current helper uses write/rename without an explicit filesystem sync (`save.ts:831`). It provides atomic replacement behavior, not evidence of power-loss durability. For the Task 6 durable boundary, sync written staging content before publication and handle directory metadata sync where the host filesystem supports it; state the tested process-crash versus power-loss guarantee honestly. Keep all fallible candidate construction/validation before commit, and do not introduce a post-commit error that is misreported as a safe pre-commit failure.
